AHow to use this page

A single source of truth for what to build and how to build it.

  1. Skim the workflow once — it's how every change moves from idea to main.
  2. Open the feature board, find one tagged Open at your priority, and claim it (see Communication).
  3. Cut a branch (branching rules), commit in the agreed format (commit rules), open a PR (PR rules).
  4. Get one review, merge with squash, delete the branch. Move the feature to Done.
Rule of thumb: if you're unsure whether your change needs a discussion, open a draft PR early — it's the cheapest way to align before you spend a day going the wrong direction.

DBranching

One feature, one branch, one PR, one squash-merge. Branches are cheap; long-lived branches are not.

Branch naming

<type>/<feature-id>-<short-slug>

# examples
feat/F-020-incident-service
feat/F-051-in-app-camera
fix/F-030-wo-state-machine-pause-bug
chore/F-001-bump-turbo-2.0
docs/playbook-update-pr-template
spike/realtime-map-websocket-vs-sse
PrefixUse for
feat/New feature or significant new behaviour
fix/Bug fix in existing behaviour
chore/Tooling, deps, config — no user-facing change
refactor/Code restructuring without behaviour change
docs/Documentation only
spike/Throwaway exploration; spikes are not merged

Rules

  • Branch off the latest main, not someone else's feature branch.
  • Keep branches short-lived (≤ 5 working days). If longer, split the feature.
  • Rebase on main daily if you're going to take more than a day, to surface conflicts early.
  • Delete the branch immediately after merge (the GitHub setting will offer to do this for you).
  • Never reuse a branch name — once merged, that name is gone.

ECommits

Conventional Commits. Small, focused, present-tense. The history is read more than it's written.

Format

<type>(<scope>): <short summary, imperative mood, lowercase, no trailing period>

[optional body — wrap at 72 cols, explain the WHY, not the WHAT]

[optional footer — refs F-XXX, BREAKING CHANGE: ...]

Examples

feat(incident): add duplicate detection by proximity + category

Two incidents within 50m and same category within 1h
are flagged as potential duplicates. Engineer can confirm
or split.

Refs F-020

---

fix(wo): prevent close on paused work order

Previously the closure handler ignored the paused state;
this caused phantom-closed WOs in the dashboard.

Refs F-030

---

chore(deps): bump expo to 50.0.7

Types

feat · fix · chore · refactor · docs · test · perf · build · ci

Do

  • Commit often — every logical step (a passing test, a working module).
  • Write the message before staging — it forces clarity.
  • Reference the feature ID — it links the commit to the feature board.

Don't

  • Don't squash 800 lines of unrelated work into one commit.
  • Don't write fix stuff, wip, or final.
  • Don't commit commented-out code, dead branches, or console.log.

FPull requests

A PR is a conversation about a change. Make it easy for the reviewer to say yes.

Size

  • Target ≤ 400 lines changed (excluding lockfiles, generated code, snapshots).
  • Above 400, split. Above 800, the reviewer can reject on size alone.
  • If the feature is genuinely large, ship it as a sequence of PRs behind a feature flag.

PR title

<type>(<scope>): <summary>   [F-XXX]

# examples
feat(incident): add capture screen with offline support   [F-021]
fix(evidence): retry chunked upload on 503                [F-052]

PR description template

## What
<one-paragraph summary of the change>

## Why
<the user-visible or operational reason — link the feature ID>
Refs: F-XXX

## How
<the approach in 3-5 bullets — call out any non-obvious decisions>

## Screenshots / Recordings
<mobile + web screenshots for any UI change; before + after for fixes>

## Test plan
- [ ] Unit tests added / updated
- [ ] Integration test added / updated
- [ ] Manually tested on iOS / Android / web
- [ ] Verified offline → online sync
- [ ] DB migration is reversible (if applicable)

## Risk & rollback
<what could break, and how do we roll back>

PR lifecycle

  1. Open as draft as soon as you have something compilable — the reviewer can sanity-check direction early.
  2. Push commits as you go; mark Ready for review when CI is green and the description is filled in.
  3. Address review comments by new commits (not force-push, until ready to merge).
  4. Once approved + CI green, the author merges. Use Squash and merge. The squashed title becomes the merge commit subject — re-check it.
  5. Delete the branch.
Required to merge: 1 approving review · all CI checks green · no unresolved review threads · branch up-to-date with main.

GCode review

A review is a gift to the author and to the codebase. It is not gatekeeping.

Service levels

PR sizeFirst review within
≤ 100 lines4 working hours
≤ 400 lines1 working day
> 400 linesAuthor should split — but if accepted: 2 working days

What a reviewer looks for

  • Correctness — does it do what the PR says? Did you check edge cases?
  • Tests — meaningful, not just coverage padding.
  • Boundaries — does this leak responsibility across services? Cross-service DB queries are a red flag.
  • Migrations — reversible? Safe on a non-empty table?
  • Security — input validation at the boundary, no secrets in code, no SQL string interpolation.
  • Performance — N+1 queries, unbounded lists, missing indexes.
  • Naming & readability — would a teammate cold-read this in 6 months?

Comment etiquette

Use prefixes to signal severity, so the author knows what's blocking vs. taste:

  • blocking: must be addressed before merge.
  • consider: suggestion, author's call.
  • nit: style/minor; ignore freely.
  • question: I don't understand — please explain.
  • praise: this is nicely done. (Use these too — reviews shouldn't be only criticism.)

HDefinition of Done

A feature isn't done when the code compiles. It's done when this list is satisfied.

  • Acceptance criteria of the feature card are met.
  • Unit tests cover the new logic; existing tests still pass.
  • Integration test added for any new API endpoint or state transition.
  • Manually verified on the target platform (iOS & Android for mobile; Chrome + Safari for web).
  • For mobile: offline path verified (capture offline → sync online → server state correct).
  • DB migrations are reversible and run cleanly on a copy of dev data.
  • API contract change is reflected in OpenAPI spec; SDK regenerated.
  • Inline docs/comments only where the WHY is non-obvious; no decorative comments.
  • No new linter or type-check warnings.
  • Telemetry (logs/metrics) added for any new failure mode worth alerting on.
  • Feature flag added if the change is risky or partial.
  • PR description filled in; screenshots attached for UI; risk & rollback noted.
  • One approving review; all CI checks green.
  • Feature moved to Done on the board; teammates notified in the daily async update.

ITesting

Test the thing that would page someone at 2am if it broke. Don't test what the framework already guarantees.

Unit (fast, many)

Pure functions, state machines, validators, geo math. Vitest (web/backend) & Jest (mobile). Should run in < 30 s locally.

Integration (medium, fewer)

API + DB + queue in a real Postgres & Redis (Docker). One per endpoint family. Run on every PR.

End-to-end (slow, very few)

Playwright for web; Detox or Maestro for mobile. Cover only the golden paths (incident → WO → evidence → closure).

What we don't test

  • Don't unit-test trivial getters/setters or pure mappings.
  • Don't mock the database in integration tests — use a real Postgres in Docker.
  • Don't write snapshot tests for UI unless the component is purely presentational.
Coverage isn't the metric. A change with 100% coverage and no integration test is weaker than a change with 60% coverage and a real end-to-end check. We measure tests by the bugs they would have caught.

JCode standards

Automated where possible. The tools are the source of truth — don't argue about formatting.

Formatting

Prettier on save, enforced in CI. No manual formatting debates.

Linting

ESLint with the project config. Warnings are errors in CI.

Types

TypeScript strict across everything. Shared types live in packages/domain-types.

Imports

Workspace-relative imports (@hoc/...). No deep imports across service boundaries.

File size

Aim for < 300 lines per file; split when a file grows two responsibilities.

Comments

Write the WHY, never the WHAT. If the code needs a comment to explain what it does, rename the variables.

Pre-commit hook

# installed via husky + lint-staged
pre-commit:
  - prettier --check
  - eslint --max-warnings 0
  - tsc --noEmit
  - related unit tests

KData & API contracts

The database and the API are the contracts that bind us. Changes to them deserve extra care.

Database migrations

  • One migration per PR; each migration is reversible (up and down).
  • For destructive changes (drop column, drop table): two-PR pattern — first stop writing, ship, then drop in a follow-up.
  • Add an index in the same PR as the query that needs it.
  • Never edit a migration that's already been merged — write a new one.
  • Test the migration on a snapshot of dev data before opening the PR.

API changes

  • OpenAPI spec is updated in the same PR as the implementation.
  • Generated SDK is regenerated and committed.
  • Additive changes are fine. Breaking changes require a deprecation period and a version bump.
  • All mutating endpoints must accept an idempotency key — this is non-negotiable for the offline sync path.

Service boundaries

Each service owns its tables. If your code needs data from another service's table, call the service's API or subscribe to its events. Cross-service JOINs in the database are a blocking review comment.

Secrets

  • Never commit a real key, token, or password. Pre-commit hook blocks common patterns.
  • Local: .env.local (gitignored). Cloud: managed in the secrets store, injected at runtime.
  • If a secret leaks, rotate it immediately and tell the team — no blame, just rotation.

LCommunication & claiming a feature

With a 2–3 person team, ceremony is the enemy. Lightweight rituals, high transparency.

Claiming a feature

  1. Pick a feature with status Open, priority you can take, and no unmet dependency.
  2. Post in the team channel: "Taking F-021 incident capture screen. Estimate: 3 days."
  3. Move the status to Claimed on the board (or update this page if that's where the team tracks state).
  4. When you open the draft PR, move to In progress. When ready: In review. After merge: Done.

Daily async standup

One post per person, before noon, three lines:

Yesterday: shipped F-020 backend; opened PR for F-022 triage screen.
Today:     review F-021; start F-023 incident map.
Blockers:  need design decision on duplicate-merge UX — will DM Owner.

Weekly sync (30 min)

  • Walk the board: what shipped, what's stuck, what's next.
  • Re-prioritise if reality has changed (it usually has).
  • One architectural topic per week — keep the technical debt conversation alive.

Avoiding collisions

Do

  • Claim before you start; if you abandon, un-claim.
  • Touch a shared file (domain-types, api-client)? Mention it in standup.
  • Rebase on main daily.
  • Pair-programme on the hard 30 min of a feature, not the easy 8 hours.

Don't

  • Don't silently start a feature someone else might be eyeing.
  • Don't sit on a PR for more than a working day without a status update.
  • Don't let a branch live longer than the feature you're building.
  • Don't refactor adjacent code in a feature PR — open a separate refactor/ PR.
One sentence to take away: small features, short branches, fast reviews, honest commits. Everything else is detail.
